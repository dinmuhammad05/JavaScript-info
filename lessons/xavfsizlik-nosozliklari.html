Ba'zan zaiflik kodning o'zida emas, balki tizim qanday sozlanganida yashiringan bo'ladi. Standart parol o'zgartirilmagan, xato xabari haddan ziyod ko'p ma'lumot beryapti, eskirgan paket yamalmagan — bularning barchasi hujumchiga eshik ochadi. Bu yakuniy darsda biz konfiguratsiya va sozlash bilan bog'liq zaifliklarni hamda ularning himoyasini ko'rib chiqamiz.

Security Misconfiguration

Xavfsizlik noto'g'ri sozlangani (Security Misconfiguration) — OWASP Top 10ning eng keng tarqalgan bandlaridan biri. U kodda emas, balki tizim, server yoki freymvork sozlamalarida qoldirilgan kamchiliklardan iborat.

Eng ko'p uchraydigan ko'rinishlari:

  • Standart parollar: admin panel yoki ma'lumotlar bazasi standart login/parol bilan qolgan;
  • Ochiq portlar va xizmatlar: kerak bo'lmagan xizmatlar tashqi olamga ochiq;
  • Batafsil xato xabarlari: foydalanuvchiga to'liq xato izi (stack trace), fayl yo'llari yoki baza tuzilishi ko'rsatiladi;
  • Yangilanmagan paketlar: ma'lum zaiflikka ega eski kutubxonalar ishlatilmoqda;
  • Ortiqcha ruxsatlar: katalog ro'yxati ochiq, debug rejimi ishga tushirilgan holda qolgan.

Himoyasi — har bir sozlamani ongli tekshirish:

  • Barcha standart parollarni o'zgartiring va kuchli parollar qo'ying;
  • Ishlatmaydigan xizmat va portlarni o'chiring;
  • Foydalanuvchiga umumiy, qisqa xato xabari ko'rsating; to'liq tafsilotni faqat serverda logga yozing;
  • Debug rejimini ishlab chiqarish (production) muhitida o'chiring.

Sezgir ma'lumotni oshkor qilish

Maxfiy ma'lumot — parollar, API kalitlari, tokenlar, shaxsiy ma'lumot — noto'g'ri joyda saqlansa yoki tashqariga chiqib ketsa jiddiy muammo. Ikki keng tarqalgan xato:

  • Kodda yashirin sirlar (secrets): API kaliti yoki parolni to'g'ridan-to'g'ri kodga yozib, uni versiya nazorati (git) ga jo'natish;
  • Logda maxfiy ma'lumot: parol, token yoki karta raqamini logga yozib qo'yish.
// ZAIF: sir to'g'ridan-to'g'ri kodda
const apiKalit = 'sk_live_123456789maxfiy';

// XAVFSIZ: sir muhit o'zgaruvchisidan olinadi
const apiKalit2 = process.env.API_KALIT;
// .env fayli git'ga JO'NATILMAYDI (.gitignore ga qo'shiladi)
  • Sirlarni muhit o'zgaruvchilarida (environment variables) yoki maxsus sir-boshqaruv tizimida saqlang;
  • .env faylini .gitignorega qo'shing — u hech qachon repozitoriyga tushmasin;
  • Logga yozishdan oldin maxfiy maydonlarni (parol, token) niqoblang yoki olib tashlang;
  • Agar sir tasodifan oshkor bo'lsa, uni darhol bekor qilib, yangisini yarating.
Bir marta git tarixiga tushgan sir "o'chirib tashladim" desangiz ham tarixda qolaveradi. Yagona to'g'ri javob — o'sha sirni darhol bekor qilib (revoke), yangi kalit yaratishdir.

Log yozishdan oldin maxfiy maydonlarni niqoblash g'oyasini kod bilan ko'raylik. Quyidagi demo obyektdan sezgir maydonlarni logga chiqishdan avval yashiradi:

log-tozalash.js
// natija shu yerda chiqadi

Endi log faylida parol yoki token ko'rinmaydi. Bu — maxfiy ma'lumot oshkorligining oldini olishning oddiy, ammo samarali usulidir.

XXE — XML External Entity

XXE (XML External Entity) — XMLni qayta ishlovchi dasturlarda uchraydigan zaiflik. XML formati "tashqi obyekt" (external entity) degan xususiyatni qo'llab-quvvatlaydi, bu esa hujjat tashqi manbaga murojaat qilishga imkon beradi.

Agar XML tahlilchisi (parser) tashqi obyektlarni yoqilgan holda ishlasa, hujumchi maxsus tuzilgan XML orqali serverni tashqi yoki ichki resurslarni o'qishga majburlashi mumkin — bu SSRFga o'xshash natijaga olib keladi.

Himoyasi konseptual jihatdan oddiy — tashqi obyektlarni o'chirish:

  • XML tahlilchisida tashqi obyekt (external entity) va DTD qayta ishlashni o'chirib qo'ying;
  • Iloji bo'lsa, XML o'rniga soddaroq va xavfsizroq format (masalan, JSON) ishlating;
  • XML tahlilchisini xavfsiz standart sozlamada ishga tushiring.
Zamonaviy ko'plab XML kutubxonalari tashqi obyektlarni standart holatda o'chirib qo'ygan. Ammo bunga ishonch hosil qilish — sizning zimmangizda. "Standart xavfsiz" degan taxminni har doim tekshiring.

Ishonchsiz deserializatsiya

Deserializatsiya — saqlangan yoki uzatilgan ma'lumotni (masalan, matn) qaytadan dastur obyektiga aylantirish jarayoni. Agar dastur ishonchsiz manbadan kelgan ma'lumotni tekshirmasdan deserializatsiya qilsa, hujumchi maxsus tuzilgan ma'lumot orqali dasturning kutilmagan tarzda ishlashiga sabab bo'lishi mumkin.

  • Ishonchsiz manbadan kelgan ma'lumotni hech qachon ko'r-ko'rona deserializatsiya qilmang;
  • Ma'lumot butunligini tekshiring (masalan, imzo yoki tekshiruv summasi bilan);
  • Iloji bo'lsa, faqat ma'lumot tashuvchi oddiy formatdan (JSONni sxema validatsiyasi bilan) foydalaning, ijro etuvchi formatlardan emas.

Xavfsizlik sarlavhalari

HTTP javob sarlavhalari brauzerga qo'shimcha himoya ko'rsatmalari berishda muhim rol o'ynaydi. Ular arzon, ammo samarali qatlam:

  • Content-Security-Policy: resurslar qayerdan yuklanishini cheklaydi (XSSga qarshi);
  • Strict-Transport-Security: brauzerni faqat HTTPS ishlatishga majburlaydi;
  • X-Content-Type-Options: brauzerni kontent turini "taxmin qilishdan" to'xtatadi;
  • X-Frame-Options: sahifani begona freymda ochilishdan himoya qiladi (clickjackingga qarshi).
Express ilovasida helmet kabi kutubxonalar bu xavfsizlik sarlavhalarini avtomatik o'rnatib beradi. Bir qator kod bilan bir necha himoya qatlamini qo'shish mumkin — bu arzon va foydali odat.

Xavfsiz standart sozlama cheklisti

Yakunda, konfiguratsiya bilan bog'liq zaifliklardan himoyalanish uchun umumiy cheklist:

  • Standart parollarni o'zgartiring: hech bir tizim zavod sozlamasida qolmasin;
  • Keraksiz narsani o'chiring: ishlatmaydigan xizmat, port, funksiya va debug rejimini o'chiring;
  • Sirlarni ajrating: API kalit va parollarni koddan emas, muhit o'zgaruvchisidan oling;
  • Xato xabarini cheklang: foydalanuvchiga qisqa xabar, logga to'liq tafsilot;
  • Paketlarni yangilab turing: npm audit orqali zaif bog'liqliklarni muntazam tekshiring;
  • Xavfsizlik sarlavhalarini qo'shing: helmet yoki teng vositalar bilan;
  • Tashqi obyektni o'chiring: XML ishlatsangiz, external entityni yoqmang;
  • Xavfsiz standartni tanlang: tizimni eng cheklangan holatda ishga tushirib, keyin kerak bo'lsa oching.
Bitta oltin qoida bilan yakunlaymiz: standart sozlamalar ko'pincha xavfsiz emas — ular qulaylik uchun ochiq qilib qo'yilgan bo'ladi. Har bir tizimni ishga tushirganda uni ongli ravishda qattiqlashtiring (harden), "ishlayapti" degani "xavfsiz" degani emasligini unutmang.
Ushbu bob davomida biz OWASP Top 10ning eng muhim bandlarini — kirish nazorati, Injection, XSS, CSRF/SSRF va noto'g'ri sozlashni — himoya nuqtai nazaridan ko'rib chiqdik. Esda tuting: xavfsizlik — bir martalik ish emas, balki doimiy jarayon. Kiritmaga ishonmang, har qatlamda tekshiring va tizimlaringizni muntazam yangilab, qattiqlashtirib turing.
